# Migrations Strategy

Implemented by `src/database/migrations.py` (`SCHEMA_VERSION = 2`), proven by
`tests/test_migrations.py` (3 tests). Decision rationale: [ADR-002](../architecture/decisions/ADR-002-persistence-and-migrations.md).

## 1. How it works

```
bootstrap()
  └── Database(url)
        └── run_migrations(engine)
              1. Base.metadata.create_all()            # idempotent, new installs
              2. ensure schema_version table
              3. seed version 1 row if empty
              4. inspector-based additive column pass
              5. record version 2 if all v2 columns present
```

Key properties:

- **Idempotent:** running twice is safe (tested).
- **Partial-state tolerant:** each column is checked with
  `inspect(engine).get_columns(table)` before `ALTER TABLE ... ADD COLUMN`.
- **Additive only:** no `DROP`, no `RENAME`, no type change, no data backfill.
- **Portable DDL:** `INTEGER`, `BOOLEAN DEFAULT 0`, `VARCHAR(n)`, `TEXT` — valid in
  SQLite and (likely) Postgres, though **Postgres is untested**.

Because every added column is either nullable or has a default, existing rows remain
valid without a backfill.

## 3. Adding a migration (maintainer checklist)

1. Change the model(s) in `src/database/models/__init__.py`.
2. Increment `SCHEMA_VERSION` in `migrations.py`.
3. Add the column(s) to `_ADDED_COLUMNS` as `("column_name", "DDL fragment")`.
4. If the column is `NOT NULL`, give it a `DEFAULT` (SQLite requires one for
   `ADD COLUMN` on a non-empty table).
5. Add a test to `tests/test_migrations.py` that starts from the previous schema and
   asserts the column exists afterwards.
6. Update [`artifacts/database/schema.sql`](../../artifacts/database/schema.sql) and
   [`data-dictionary.md`](data-dictionary.md).
7. Update `docs/project/implementation-log.md`.

## 4. What this strategy cannot do

| Change | Supported? | Workaround |
| --- | --- | --- |
| Add table | ✔ (via `create_all`) | — |
| Add nullable/defaulted column | ✔ | — |
| Add `NOT NULL` without default | ✘ | add with default, or rebuild |
| Rename column/table | ✘ | rebuild + copy, or adopt Alembic |
| Drop column | ✘ | leave it, or rebuild |
| Change type | ✘ | rebuild |
| Data transformation | ✘ | one-off script (documented in the runbook) |
| Downgrade | ✘ | restore backup |

**Rebuild recipe (manual, for renames):**

```sql
PRAGMA foreign_keys = OFF;
BEGIN;
CREATE TABLE users_new (...);
INSERT INTO users_new SELECT ... FROM users;
DROP TABLE users;
ALTER TABLE users_new RENAME TO users;
COMMIT;
PRAGMA foreign_keys = ON;
```

A rebuild must be executed by the operator with a backup in hand — it is not
automated, and no such migration exists today.

## 5. Upgrade procedure for self-hosters

```bash
# 1. Back up (always)
docker compose exec bot sqlite3 /app/data/bot.db ".backup '/app/data/backup.db'"

# 2. Pull and restart — migrations run at boot
docker compose pull && docker compose up -d

# 3. Verify
docker compose logs --tail=100 bot | grep -i migration
```

Rollback = stop the container, restore `backup.db` over `bot.db`, start the previous
image tag.

## 6. When to adopt Alembic (TASK-303)

Adopt when **any** of these becomes true:

1. A rename or destructive change is required by a shipped feature.
2. A data backfill must run transactionally with a schema change.
3. More than one deployment environment needs version pinning/rollback.
4. A second developer needs autogenerated revision history.

Migration path: baseline Alembic at the v2 schema (`alembic stamp`), keep the runner
until the baseline is applied everywhere, then delete `migrations.py`.

## 7. Testing requirements for any schema change

| Test | Assertion |
| --- | --- |
| Fresh install | all tables/columns exist; `schema_version` = current |
| Re-run | no error, no duplicate version rows |
| Legacy upgrade | starting from the previous schema, the new column exists with defaults |
| Repository behaviour | the new field is readable/writable through its repository |

## 8. Known risks

- **No automatic backup before DDL.** A failed upgrade can leave a half-migrated DB.
  Mitigation: the runner adds columns one at a time and each check is independent, so
  a retry resumes rather than fails.
- **Two processes migrating at once** would race. Mitigation: single-replica rule.
- **`schema_version` can disagree with reality** if someone edits the DB by hand. The
  inspector check is what actually decides, so this is tolerated.
